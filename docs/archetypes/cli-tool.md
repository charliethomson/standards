# Archetype: CLI / service tool

A standalone binary distributed to machines (not a hosted service with clients). It may be
its own repo or a `bin/` member inside a product monorepo. The distinguishing feature is
**distribution through the registry with an install manifest**.

Reference: a `someproduct` CLI and a `worker` (a background companion service).

## Repo shape

```
<tool>/  (or bin/<tool>/ inside a product)
├── Cargo.toml
├── build.rs                version derivation (+ optional libbuildinfo emit)
├── src/main.rs             clap entrypoint; product_name!("dev.thmsn.<product>.cli")
├── completions/            shipped shell completions (or generated by a subcommand)
├── .woodpecker/            cli.release.yml → publish to registry (see ci-cd.md naming)
├── .standards.conf         PRODUCT / ARCHETYPE identity (or the parent monorepo's)
└── AGENTS.md               Standards: line (archetype, product) + repo overrides
```

## Registry distribution

Published with `kind = cli`, which supports **multi-target artifacts** (one per
os/arch/libc) under a single version, plus an **install manifest** describing how to set it
up on a machine:

```json
{
  "bin_name": "<tool>",
  "version_command": ["<tool>", "--version"],
  "symlinks": { "<alias>": "<tool>" },
  "man": ["man/<tool>.1"],
  "completions": {
    "bash": { "generate": ["<tool>", "completions", "bash"] },
    "zsh":  { "generate": ["<tool>", "completions", "zsh"] },
    "fish": { "bundled": "completions/<tool>.fish" }
  }
}
```

Install is via the registry's platform-detecting installer (`GET /install/<slug>` for
Unix, `…/install/<slug>.ps1` for Windows), which selects the right artifact, verifies the
SHA-256, and applies the manifest. Publish per release with
`charliethomson/registry/.github/actions/publish@main` (or `scripts/registry-publish.sh`).
See [registry-publishing.md](../registry-publishing.md).

## Signing in to a product

A CLI that calls a product's API (or the registry) signs in through Authelia as a **public
client**, never with a password prompt of its own:

- `<tool> login` reads `GET /api/auth/config` from the server URL it was given, then runs the
  **device authorization grant** (RFC 8628): print the verification URL and code, poll the
  token endpoint at the given `interval`, back off on `slow_down`. Loopback PKCE is the
  fallback where a browser is on the same machine.
- One client may request several audiences (say a product and the registry), so one sign-in
  serves every product the CLI talks to.
- The refresh token is stored and rotated per [refresh-tokens.md](../refresh-tokens.md).
  `liboidc`'s `client` feature does all of this; don't hand-roll it.

See [auth-integration.md](../auth-integration.md#native-and-cli-clients).

## Checklist

- [ ] `build.rs` derives the version; `--version` reports it (plus commit hash via `libbuildinfo`).
- [ ] `product_name!("dev.thmsn.<product>.<tool>")` declared **and published with
      `set_global()`** at the top of `main` ([`../identifiers.md`](../identifiers.md)).
- [ ] `.woodpecker/cli.release.yml` builds per-target artifacts on self-hosted agents.
- [ ] Published to the registry as `kind = cli` with a complete install manifest.
- [ ] Shell completions shipped or generated by a subcommand.
- [ ] If it calls a product: signs in with the device flow as public client `<slug>-cli`,
      discovers the issuer from `GET /api/auth/config`, stores the refresh token `0600`.
- [ ] Command/parsing logic tested.
- [ ] Root `README.md` leads with the registry install one-liner (and that re-running it
      upgrades), then a subcommand tour and config/completions
      ([`../readmes.md`](../readmes.md)).
